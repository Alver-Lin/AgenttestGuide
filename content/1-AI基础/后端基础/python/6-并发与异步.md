# 并发与异步：选择模型，控制任务，可靠收尾

本篇对应蛇形图 **L6，节点 31–36**，前置为 [5-标准库主干](./5-标准库主干.md)。目标是理解任务如何重叠执行，以及如何限制并发、接收结果、处理异常和停止任务。

验证环境为 **Python 3.12**。除节点 35 的 HTTPX 示例外，代码只用标准库；HTTPX 示例使用模拟传输，不访问互联网。涉及多进程的代码请保存为 `.py` 文件运行；其余普通 Python 代码块可独立运行。文中的 `asyncio.run()` 面向独立脚本，在已经运行事件循环的交互环境中应直接 `await` 协程。

## 31｜并发模型选型

### 31.1 并发、并行与异步

**并发**是多个任务在一段时间内交替推进；**并行**是多个任务在同一时刻执行；**异步**是一种在等待操作完成时交出控制权的编程方式。用了 `async def` 不代表自动变快，也不代表每个函数都会并行运行。

先观察任务主要在做什么：

- **IO 密集**：等待网络、磁盘或其他服务。阻塞式库可以配线程；支持异步接口的库可以配 `asyncio`。
- **CPU 密集**：大量纯 Python 计算。常见选择是进程池、优化算法，或使用能在原生层计算的库。
- **规模小、耗时短**：顺序执行可能更简单、更快。创建任务、通信和切换都有成本。

例如下载多个文件通常在等待网络；逐像素执行 Python 循环通常在计算；读取后再压缩文件则混合了 IO 与计算，需要实际测量。

### 31.2 GIL 是有条件的实现特征

常规 CPython 构建中的全局解释器锁（GIL）通常限制同一进程里多个线程同时执行 Python 字节码。因此，不要期待给纯 Python 计算加线程就获得多核加速。

但 GIL 不等于“线程无法并发”：许多 IO 操作和部分原生扩展会释放它。它也不等于“共享数据天然安全”，一组读写操作仍可能被其他线程穿插。

Python 3.13 起提供可选的自由线程构建；具体构建、扩展兼容性和是否重新启用 GIL 会影响行为。应检查实际运行环境，而不是把“Python 永远有 GIL”当作语言定义。参见 [自由线程 Python 文档](https://docs.python.org/3/howto/free-threading-python.html)。

### 31.3 选择之前先回答四个问题

1. 主要等待什么，还是主要在计算？
2. 现有依赖提供同步接口还是异步接口？
3. 数据能否拆成独立任务，传输和复制成本有多大？
4. 任务失败或用户退出时，正在进行的工作如何停止？

并发上限受连接池、文件句柄、内存、远端限流等约束。把任务数从 10 改成 10000，不等于吞吐量会同步增长。

**练习**：为批量 HTTP 请求、纯 Python 大循环、几十个短文本转换各选一种起步方案，并说明为什么。

**掌握标志**：能先描述瓶颈和约束，再选择模型。

## 32｜线程与进程

### 32.1 线程：共享内存，也共享风险

```python
import threading
from queue import Queue


def worker(jobs, results):
    while True:
        item = jobs.get()
        try:
            if item is None:
                return
            results.put(item * item)
        finally:
            jobs.task_done()


jobs = Queue()
results = Queue()
threads = [threading.Thread(target=worker, args=(jobs, results)) for _ in range(2)]
for thread in threads:
    thread.start()
for number in [1, 2, 3]:
    jobs.put(number)
for _ in threads:
    jobs.put(None)

jobs.join()
for thread in threads:
    thread.join()
print(sorted(results.get_nowait() for _ in range(3)))
```

```text
[1, 4, 9]
```

`Queue` 提供线程间安全的任务传递；每次 `get()` 都要配一次 `task_done()`，包括退出用的哨兵。`jobs.join()` 等待任务被确认完成，`thread.join()` 等待线程退出，两者等待的条件不同。

这里的工作只是不会失败的整数平方。真实工作应在工作线程内捕获可预期的任务异常并传回结果，否则线程退出后，队列可能还有未完成项，让 `join()` 一直等待。并发结果的到达顺序也不一定等于提交顺序，因此示例排序后展示。

### 32.2 锁：保护完整的状态变更

```python
import threading

counter = 0
lock = threading.Lock()


def increase():
    global counter
    for _ in range(1000):
        with lock:
            counter += 1


threads = [threading.Thread(target=increase) for _ in range(2)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
print(counter)
```

```text
2000
```

锁保护共享状态的整个操作，不只是某一行看起来复杂的表达式。多个锁顺序不一致可能造成死锁；持锁等待网络会扩大阻塞。优先减少共享数据，必要时再加锁。

`threading.local()` 适合每个线程自己的状态；`Event` 用来通知停止或就绪；`Condition` 用于围绕条件等待。不要用任意 `sleep()` 代替可靠的状态同步。

### 32.3 进程：独立内存与显式通信

保存以下代码为 `process_demo.py` 再运行：

```python
import multiprocessing as mp


def square(number, sender):
    try:
        sender.send(number * number)
    finally:
        sender.close()


if __name__ == "__main__":
    context = mp.get_context("spawn")
    receiver, sender = context.Pipe(duplex=False)
    process = context.Process(target=square, args=(7, sender))
    process.start()
    sender.close()
    try:
        if not receiver.poll(10):
            raise TimeoutError("子进程未及时返回")
        print(receiver.recv())
        process.join(timeout=10)
        if process.is_alive():
            raise TimeoutError("子进程未及时退出")
        print(process.exitcode)
    finally:
        receiver.close()
        if process.is_alive():
            process.terminate()
            process.join()
        process.close()
```

```text
49
0
```

`spawn` 启动新的解释器；子进程需要重新导入主模块，因此创建进程必须放在入口保护中，目标函数定义在模块顶层。通信数据通常需要可序列化，普通局部函数和 lambda 不适合作为进程任务。

不同操作系统和 Python 版本的默认启动方式并不一致。本例显式使用 `spawn`，避免依赖平台默认值；可查 [multiprocessing 文档](https://docs.python.org/3/library/multiprocessing.html)。

修改子进程中的普通列表不会自动修改父进程列表。共享内存、队列和管道都需要明确的生命周期。`terminate()` 是最后的强制收尾手段，不保证子进程的 `finally` 执行，不能作为日常提交数据的方式。

**练习**：将平方任务改成多个独立批次，比较线程共享列表与进程返回结果的区别。

**掌握标志**：能解释线程共享内存、进程隔离内存，以及为什么进程需要入口保护。

## 33｜任务池

### 33.1 Executor：复用执行资源

```python
from concurrent.futures import ThreadPoolExecutor


def square(number):
    return number * number


with ThreadPoolExecutor(max_workers=2) as executor:
    results = list(executor.map(square, [3, 1, 2]))
print(results)
```

```text
[9, 1, 4]
```

`map()` 的结果按输入顺序产生，即使后面的任务先完成，也要等待前面的结果。任务很多时注意提交和内存成本，不能把“最多两个工作线程”理解成“系统里只保存两个任务”。

CPU 密集且可序列化的任务可以使用 `ProcessPoolExecutor`，同时遵守节点 32 的顶层函数和主入口要求，并显式考虑进程启动方式。

### 33.2 Future：尚未完成的结果

```python
from concurrent.futures import ThreadPoolExecutor, as_completed


def reciprocal(number):
    return 1 / number


results = {}
with ThreadPoolExecutor(max_workers=2) as executor:
    futures = {executor.submit(reciprocal, n): n for n in [2, 0, 4]}
    for future in as_completed(futures):
        number = futures[future]
        try:
            results[number] = future.result()
        except ZeroDivisionError:
            results[number] = "不能除零"
print(sorted(results.items()))
```

```text
[(0, '不能除零'), (2, 0.5), (4, 0.25)]
```

`submit()` 返回 `Future`，`.result()` 取得结果或重新抛出任务异常；`as_completed()` 按完成顺序交出 Future。上例最后排序只是为了稳定展示，不代表实际完成顺序。

如果提交后从不检查结果，异常可能被忽略。不要让同一个小线程池里的任务互相等待彼此的 Future，资源耗尽时可能死锁。

### 33.3 超时与取消的边界

- `future.result(timeout=...)` 限制调用方等待时间，不会因此杀死运行中的函数。
- `future.cancel()` 通常只能取消尚未开始的任务；返回 `False` 可能意味着已经开始或结束。
- `with Executor(...)` 退出时通常等待正在执行的任务完成。因此捕获等待超时后，程序未必立即退出。
- 想提前停止长任务，需要让函数周期性检查停止信号，并为内部 IO 设置超时。

线程池和进程池的具体取消、关闭语义见 [concurrent.futures 文档](https://docs.python.org/3.12/library/concurrent.futures.html)。

**练习**：同时提交成功和失败任务，为每个输入保留结果状态，不因一项失败丢掉其他结果。

**掌握标志**：能区分“停止等待”“取消未开始任务”和“停止运行中的工作”。

## 34｜异步 IO

### 34.1 协程、Task 与事件循环

```python
import asyncio


async def fetch_score(name, score):
    await asyncio.sleep(0.01)
    return name, score


async def main():
    results = await asyncio.gather(
        fetch_score("小林", 85),
        fetch_score("小周", 58),
    )
    print(results)


asyncio.run(main())
```

```text
[('小林', 85), ('小周', 58)]
```

调用 `async def` 函数得到协程对象，函数体不会因此完整执行。`await` 等待可等待对象；`create_task()` 将协程调度为 Task；事件循环负责推进任务。

`gather()` 可以并发调度这些协程，结果顺序对应参数顺序。下面两种写法不同：先 `await a()` 再 `await b()` 通常顺序执行；先创建两个 Task，再等待它们，才允许任务重叠推进。

事件循环依靠协作式切换。不是每个 `await` 都一定暂停，但调用阻塞函数会占住当前事件循环线程。异步函数里不要直接用 `time.sleep()` 模拟等待；应使用 `await asyncio.sleep()`。

### 34.2 TaskGroup：管理一组任务的生命周期

```python
import asyncio


async def double(number):
    await asyncio.sleep(0)
    return number * 2


async def main():
    async with asyncio.TaskGroup() as group:
        tasks = [group.create_task(double(n)) for n in [1, 2, 3]]
    print([task.result() for task in tasks])


asyncio.run(main())
```

```text
[2, 4, 6]
```

`TaskGroup` 从 Python 3.11 起可用，正常退出时所有子任务已经结束。某个任务出现非取消异常时，会取消其他任务并等待清理，再以异常组等形式向外报告；需要按异常类型分别处理时学习 `except*`。

与此不同，默认 `gather()` 把首个异常传播给等待者时，不会自动取消其余子任务。选择哪个工具取决于业务是否允许部分任务继续。

### 34.3 超时会涉及取消

```python
import asyncio


async def slow_job():
    try:
        await asyncio.sleep(10)
    finally:
        print("任务已清理")


async def main():
    try:
        async with asyncio.timeout(0.02):
            await slow_job()
    except TimeoutError:
        print("等待超时")


asyncio.run(main())
```

```text
任务已清理
等待超时
```

`asyncio.timeout()` 在上下文外表现为 `TimeoutError`。`wait_for()` 也是常用的超时工具；它通常取消被等待任务，并等待其处理取消，因此实际耗时可能超过指定值。

`task.cancel()` 发出取消请求，在任务接下来的取消机会处抛出 `CancelledError`。它不是立即终止代码。这个异常属于 `BaseException` 分支；显式捕获它做清理后，通常应继续 `raise`，避免破坏任务组和超时的语义。详细约定见 [asyncio 任务文档](https://docs.python.org/3.12/library/asyncio-task.html)。

### 34.4 桥接同步函数

```python
import asyncio


def blocking_library_call():
    return "同步结果"


async def main():
    result = await asyncio.to_thread(blocking_library_call)
    print(result)


asyncio.run(main())
```

```text
同步结果
```

`to_thread()` 适合把阻塞 IO 放到线程里，避免卡住事件循环；它不会把普通 CPU 计算自动变成多核并行。取消等待它的协程，也不会强制终止底层已运行的线程。

**练习**：用 TaskGroup 执行三个模拟请求，为一项设置超时，观察清理和异常传播；再区分全批失败与逐项记录失败的需求。

**掌握标志**：能说明协程何时开始、何时交出控制权、由谁等待和清理。

## 35｜异步生态与同步

### 35.1 Semaphore：限制同时进行的操作

```python
import asyncio


async def main():
    semaphore = asyncio.Semaphore(2)
    active = 0
    peak = 0

    async def job(number):
        nonlocal active, peak
        async with semaphore:
            active += 1
            peak = max(peak, active)
            try:
                await asyncio.sleep(0.01)
                return number * 2
            finally:
                active -= 1

    results = await asyncio.gather(*(job(n) for n in range(5)))
    print(results)
    print(peak <= 2)


asyncio.run(main())
```

```text
[0, 2, 4, 6, 8]
True
```

信号量限制进入某段代码的并发数量，但不限制每秒请求数。限速需要时间维度的策略。先一次性创建十万个任务再加信号量，也仍然要保存十万个 Task；大量数据应使用有界队列或分批调度。

### 35.2 Lock：保护跨 await 的状态操作

```python
import asyncio


async def main():
    count = 0
    lock = asyncio.Lock()

    async def increase():
        nonlocal count
        async with lock:
            old = count
            await asyncio.sleep(0)
            count = old + 1

    await asyncio.gather(*(increase() for _ in range(10)))
    print(count)


asyncio.run(main())
```

```text
10
```

示例故意在读写之间加入 `await`，展示任务切换。单线程事件循环中的协程也会竞争跨暂停点的共享状态。

`asyncio.Lock`、`Semaphore`、`Queue` 用于协程协作，不是跨线程同步工具。不要在协程中持有 `threading.Lock` 再等待另一个协程，否则可能阻塞整个循环。

### 35.3 HTTPX：复用异步客户端

先在练习环境安装第三方依赖：

```bash
python -m pip install httpx
```

下面的请求由 `MockTransport` 在本地应答，不依赖真实服务：

```python
import asyncio
import httpx


async def handler(request):
    return httpx.Response(200, json={"score": 85}, request=request)


async def main():
    transport = httpx.MockTransport(handler)
    async with httpx.AsyncClient(transport=transport, timeout=5.0) as client:
        response = await client.get("https://example.com/scores/1")
        response.raise_for_status()

```


实际访问服务时移除模拟 `transport`。复用客户端可以复用连接池；不要在每次循环里新建一个客户端。HTTP 状态错误、传输错误、JSON 错误和业务校验仍需分开处理。

客户端超时通常分为连接、读取、写入和连接池等待；业务总期限可以在外层配合 `asyncio.timeout()`。模拟传输适合测试请求行为与响应处理，但不能证明真实 DNS、TLS 或网络超时行为正确。参见 [HTTPX 自定义传输文档](https://www.python-httpx.org/advanced/transports/)。

**练习**：为 20 个模拟请求限制最多 3 个同时运行；模拟 HTTP 500 和无效 JSON，保留每项失败原因。

**掌握标志**：能区分并发上限、请求速率、连接池和业务总期限。

## 36｜优雅退出

### 36.1 先停止接收，再处理在途工作

退出通常包含：停止接收新工作，通知正在运行的任务，按业务决定等待或取消，保存必要状态，最后释放资源。不要只在主函数末尾打印“结束”。

线程可以通过 Event 协作退出：

```python
import threading

stop = threading.Event()
ready = threading.Event()
finished = threading.Event()


def worker():
    try:
        ready.set()
        while not stop.wait(timeout=0.1):
            pass  # 实际项目在这里执行一小步工作
    finally:
        finished.set()


thread = threading.Thread(target=worker)
thread.start()
ready.wait()
stop.set()
thread.join(timeout=2)
print(finished.is_set())
print(thread.is_alive())
```

```text
True
False
```

通知停止后，工作函数仍需要及时检查通知。不能因为设置了 daemon 线程，就假设进程退出时其中的文件写入和事务一定完成。

### 36.2 信号与 atexit 的职责

`signal` 处理操作系统信号；处理器应尽量只更新停止标记，把复杂清理留给正常控制流程。以下示例直接调用处理器模拟收到通知，不向进程发送真实信号：

```python
import signal
import threading

stop = threading.Event()


def request_stop(signum, frame):
    stop.set()


previous = signal.signal(signal.SIGINT, request_stop)
try:
    request_stop(signal.SIGINT, None)
    print(stop.is_set())
finally:
    signal.signal(signal.SIGINT, previous)
```

```text
True
```

信号注册通常必须在主解释器的主线程执行，支持的信号及事件循环信号接口因平台不同而异。在默认处理方式下，Ctrl+C 通常表现为 `KeyboardInterrupt`；注册自己的处理器会改变该行为。

`atexit.register()` 可注册正常解释器退出时的回调，但进程被强制终止、崩溃或使用 `os._exit()` 时不能指望它执行。关键资源仍应由 `with`、`try/finally` 和明确的关闭流程管理。

### 36.3 综合练习：有界异步批处理

这个离线程序用两个工作协程处理四条任务，逐项记录成功、超时和业务错误。输入顺序与结果顺序一致；队列有容量上限，避免生产者无限制堆积待处理项。

```python
import asyncio
from dataclasses import dataclass


@dataclass(frozen=True)
class Result:
    key: str
    status: str
    value: int | None = None


async def fake_fetch(key):
    if key == "slow":
        await asyncio.sleep(10)
    await asyncio.sleep(0)
    if key == "bad":
        raise ValueError("模拟业务错误")
    return len(key)


async def run_batch(keys, *, workers=2, timeout=0.05):
    if workers < 1 or timeout <= 0:
        raise ValueError("工作数与超时必须为正数")
    queue = asyncio.Queue(maxsize=workers * 2)
    results = [None] * len(keys)

    async def produce():
        for index, key in enumerate(keys):
            await queue.put((index, key))
        for _ in range(workers):
            await queue.put(None)

    async def consume():
        while True:
            item = await queue.get()
            try:
                if item is None:
                    return
                index, key = item
                try:
                    async with asyncio.timeout(timeout):
                        value = await fake_fetch(key)
                except TimeoutError:
                    results[index] = Result(key, "timeout")
                except ValueError:
                    results[index] = Result(key, "error")
                else:
                    results[index] = Result(key, "ok", value)
            finally:
                queue.task_done()

    async with asyncio.TaskGroup() as group:
        group.create_task(produce())
        for _ in range(workers):
            group.create_task(consume())
    return results


async def main():
    results = await run_batch(["alpha", "bad", "slow", "beta"])
    print([(result.key, result.status, result.value) for result in results])


asyncio.run(main())
```

```text
[('alpha', 'ok', 5), ('bad', 'error', None), ('slow', 'timeout', None), ('beta', 'ok', 4)]
```

这里把预期的逐项失败转换成状态；未知异常继续向 TaskGroup 传播，避免伪装成成功。外部取消没有被吞掉，任务组会取消生产者和消费者，并等待清理。

结果列表仍与输入一样大，所以这是“限制执行与排队数量”，不是完全恒定内存。面对无限数据流，应改成结果逐项输出，或写入数据库。示例也没有实现重试、断点续跑和跨进程强制终止；这些要依据业务单独设计。

建议验证：空输入得到空结果；单个失败不影响其他项；慢任务被标记为超时；工作数为零时明确拒绝；外部取消后没有遗留的生产者和消费者。
