# 接口常见输出方式

本文从调用和测试接口的角度，整理普通 JSON、SSE、NDJSON、WebSocket、gRPC、Webhook、异步轮询和文件下载的区别。

> 所有地址、字段、事件名和响应都是教学示例，不代表现有业务接口的真实定义。是否支持某种方式，以接口文档和实际响应为准。

## 1. 先分清：数据格式、传输方式和交互模式

平时说“接口怎么输出”，实际上可能在问不同的事情：

- **数据格式**：返回 JSON、文本、XML，还是音频、PDF 等二进制数据？
- **消息组织方式**：返回一份完整内容，还是按 SSE 事件、NDJSON 记录等方式组织？
- **通信方式**：通过普通 HTTP 请求响应，还是 WebSocket、gRPC 等通信机制？
- **交付时机**：本次请求直接拿到结果，还是先拿到任务编号，之后轮询或等待回调？

这些方式可以组合。例如，SSE 事件里的数据可以是 JSON；Webhook 通常通过另一次 HTTP 请求发送 JSON；任务轮询完成后可以返回文件下载地址。

**“普通 JSON / REST”更准确的说法是“普通 HTTP 请求，一次返回完整 JSON”。** REST 是架构风格，不是响应格式，也不规定必须一次性返回 JSON。背景见 [RESTful 使用方法](./RESTful使用方法.md) 和 [MDN：REST](https://developer.mozilla.org/zh-CN/docs/Glossary/REST)。

## 2. 普通 HTTP 响应：一次返回完整结果

### 含义与示例

客户端发起请求，服务端处理后返回一份完整业务结果。常见 JSON 响应：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"output":"这是一段完整回答。"}
```

`output` 只是示例字段名，也可能叫 `answer`、`result` 或嵌套在 `data` 中，不存在统一规定。

### 适用场景与注意点

适合普通查询、短耗时计算、配置读取，以及不需要逐步展示的问答。

- 一般在响应体读取完整后解析 JSON。
- “一次返回”指应用得到一份完整结果，不代表底层只发送一个网络包。
- 一份完整 JSON 也可能由服务端逐步写出；这并不自动成为 SSE 或 NDJSON。
- HTTP 200 之后，还要检查业务成功标志、必填字段和实际结果。

普通 HTTP 响应也可以返回 `text/plain` 文本、`application/xml` XML、`text/html` HTML 等内容；还有 `204 No Content` 这种成功但没有正文的响应。HTTP 内容与状态语义见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)。

## 3. SSE：服务端单向持续发送事件

### 含义与示例

SSE（Server-Sent Events）在一条 HTTP 响应流里持续发送事件，方向是**服务器到客户端**。适合逐步展示生成文字、任务进度和通知。

响应头中的关键标识：

```http
Content-Type: text/event-stream
```

响应体示例，每个事件以空行分隔，包括最后一个事件：

```text
event: delta
data: {"text":"你好，"}

event: delta
data: {"text":"有什么可以帮你？"}

event: done
data: {"finish_reason":"stop"}

```

`delta`、`done`、`finish_reason` 是本例自定义的业务约定，不是 SSE 强制要求。

### 如何识别和解析

- SSE 使用 UTF-8 文本，常用字段有 `data:`、`event:`、`id:`、`retry:`。
- **`event:` 可以省略。** 只有 `data: ...`、并以空行分隔的消息也可以是 SSE，不能通过“有没有 event”区分 SSE 和 NDJSON。
- `data:` 后可以是普通文本，也可以是 JSON；应先按 SSE 规则解析事件，再按约定解析数据。
- 多行 `data:` 会组成同一个事件的数据；以 `:` 开头的注释行可用作心跳，不应当作回答正文。
- `data: [DONE]` 是部分接口使用的结束约定，不是 SSE 标准，也不是 JSON。

格式说明见 [MDN：使用 SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。

### POST、重连和结束信号

浏览器原生 `EventSource` 使用 GET，其接口不提供任意请求体和自定义请求头配置。需要 POST JSON 或自定义认证头时，可以用 Fetch 等客户端读取 `text/event-stream` 响应；这时 SSE 解析和重连逻辑由所用客户端实现。

原生 EventSource 支持重连，但**重连不等于服务端一定补发遗漏事件**；续传需要事件编号和服务端配合。参见 [WHATWG：SSE 与 EventSource](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

对于有限时长的 Agent 生成任务，应按接口约定确认完成事件。连接断开可能是正常结束，也可能是网络失败，不能一律判定生成成功。

## 4. HTTP 分块、NDJSON 和原始文本流

这三者经常被混在一起，但含义不同。

### 4.1 HTTP chunked：底层如何传输响应体

HTTP/1.1 可以使用：

```http
Transfer-Encoding: chunked
```

它允许响应体分块传输，不必预先知道完整长度。块里装的可以是 JSON、SSE、文本或文件数据。

**一个传输块不等于一个业务消息。** 一条 JSON 可能跨多个块，多条消息也可能出现在同一次读取中。客户端应按应用格式识别消息边界，不能对每次网络读取的内容直接做一次 JSON 解析。

HTTP/2 和 HTTP/3 有各自的流传输机制，不使用 HTTP/1.1 的 chunked 编码。因此，没有 `Transfer-Encoding: chunked` 也可以流式返回；有它也不保证界面能实时展示，服务端、代理和客户端都可能缓冲。参见 [MDN：Transfer-Encoding](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Transfer-Encoding)。

### 4.2 NDJSON：一行一个完整 JSON 值

NDJSON 是 Newline Delimited JSON，常用媒体类型为 `application/x-ndjson`。

```http
Content-Type: application/x-ndjson
```

响应体示例，每行是一条独立记录，最后一行也以换行结尾：

```ndjson
{"type":"delta","text":"你好，"}
{"type":"delta","text":"有什么可以帮你？"}
{"type":"done","usage":{"output_tokens":12}}
```

适合持续输出结构化记录、日志、批量处理结果和模型生成事件。

- 收到字节后先缓冲，按换行拆出完整记录，再逐行解析 JSON。
- 不要把全部 NDJSON 当成一个 JSON 对象或数组解析。
- 一条记录不能用普通换行进行美化排版；字符串内部的换行要写成转义形式 `\n`。
- `type: done` 等字段仍是业务约定，不是 NDJSON 标准。

格式依据：[NDJSON 规范](https://github.com/ndjson/ndjson-spec)。

### 4.3 原始文本流：逐段传回文本

例如响应类型为 `text/plain; charset=utf-8`，服务端逐步写出“你好，”“有什么可以帮你？”等文本。

客户端可增量解码并拼接展示，但这些示意片段不一定与实际读取边界一致。UTF-8 字符也可能跨字节块，读取时应使用支持流式解码的方式。

原始文本没有 SSE 的事件结构，也没有 NDJSON 的逐行 JSON 结构。若需区分回答、进度、错误和完成，应另外约定消息格式。

### 4.4 `stream: true` 不能用来判断协议

`stream` 是接口自定义参数，不是 HTTP 标准开关。设为 `true` 后可能返回 SSE、NDJSON 或其他格式，也可能因服务端不支持而被忽略或报错。

**LLM 流式输出也可能就是 SSE。** 应结合响应的 Content-Type、正文结构和接口文档判断，不能仅凭 `stream: true` 归类。

## 5. WebSocket：双方持续发送消息

### 含义与示例

WebSocket 建立连接后，客户端和服务器都可以主动发送文本或二进制消息，地址通常以 `ws://` 或 `wss://` 开头。

示例地址：`wss://api.example.com/realtime`。

客户端发送一条消息：

```json
{"type":"input","request_id":"req-001","text":"你好"}
```

服务端返回一条消息：

```json
{"type":"delta","request_id":"req-001","text":"你好，有什么可以帮你？"}
```

客户端还可以按服务端协议发送取消或其他控制消息：

```json
{"type":"cancel","request_id":"req-001"}
```

这些 JSON 字段和命令均为示例，WebSocket 本身不规定其业务含义。

### 适用场景与注意点

适合实时语音、持续双向交互、协作和频繁控制消息。多轮 Agent 对话也可以用普通 HTTP 或 SSE 实现，并不必须使用 WebSocket。

- 按 WebSocket 消息处理数据，不要把它当作普通 HTTP JSON 响应。
- 明确认证、请求关联、心跳、取消、错误和重连规则。
- 连接关闭不一定代表某次任务完成；重连后是否恢复会话，要看应用协议。

通信能力见 [MDN：WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)。

## 6. gRPC：通过定义好的服务方法交换消息

gRPC 常用于内部服务调用，通常基于 HTTP/2，使用 Protocol Buffers 描述和编码消息。它不仅支持双向流，也支持四种调用形式：

1. **Unary**：一个请求，一个响应。
2. **Server streaming**：一个请求，多个响应消息。
3. **Client streaming**：多个请求消息，一个响应。
4. **Bidirectional streaming**：双方都可持续发送消息。

下面是 `.proto` 服务定义片段，演示服务端流和双向流；消息类型需要另外定义：

```proto
service AgentService {
  rpc Generate(GenerateRequest) returns (stream GenerateReply);
  rpc Chat(stream ChatRequest) returns (stream ChatReply);
}
```

适合有明确消息契约的服务间通信、模型推理服务和内部流式处理。是否性能更好取决于负载、实现和部署条件，不能只凭使用 gRPC 就判断。

调试通常需要 `.proto` 定义或服务器反射支持，以及能处理 gRPC 的客户端。工具可能把解码后的消息显示成 JSON，但线上传输通常不是普通 JSON 文本；应查看 **gRPC 状态**和流是否完整结束，不能只看 HTTP 200。

参见 [gRPC 官方：核心概念与调用生命周期](https://grpc.io/docs/what-is-grpc/core-concepts/)。

## 7. Webhook / 回调：结果通过另一次请求送达

### 含义与示例

调用方提供或预先注册一个回调地址；服务方在任务完成或事件发生后，主动请求这个地址，常用 HTTP POST。

在异步任务场景，可以设计为先提交任务：

```json
{
  "question": "生成本月分析报告",
  "callback_url": "https://client.example.com/callbacks/agent"
}
```

服务端立即返回受理结果，例如：

```http
HTTP/1.1 202 Accepted
Content-Type: application/json

{"task_id":"task-001","status":"queued"}
```

完成后，服务方另发一个请求：

```http
POST /callbacks/agent HTTP/1.1
Host: client.example.com
Content-Type: application/json

{"event_id":"evt-001","task_id":"task-001","status":"completed","output":"报告已生成。"}
```

这里的回调与最初提交任务是**两次独立的 HTTP 交互**。Webhook 也可用于订单变化等事件通知，并非每个 Webhook 都有“先提交任务、返回 202”这一步。

### 适用场景与注意点

适合长耗时任务、后台系统集成和事件通知。

- 调用方需要一个服务方可访问的接收地址，仅在 Apifox 中填写 URL 不会自动创建接收服务。
- 明确签名或认证校验、失败重试、去重和顺序约定。
- 回调可能重复投递；可按事件编号去重，避免重复处理业务。
- 接收端按协议及时确认接收，耗时业务可在可靠接收后异步处理。
- “已受理”“已完成”“回调投递成功”是不同状态。

重试和验签规则并无统一标准，应按具体服务实现。可参考 [Stripe 官方 Webhook 文档](https://docs.stripe.com/webhooks) 中的重复事件、投递和签名处理。

## 8. 异步任务 + 轮询：客户端主动查询结果

这是长耗时接口的另一种常见交付方式，不需要客户端提供回调地址。

### 示例流程

提交任务后收到：

```http
HTTP/1.1 202 Accepted
Location: /tasks/task-001
Retry-After: 3
Content-Type: application/json

{"task_id":"task-001","status":"queued"}
```

客户端按约定间隔请求 `GET /tasks/task-001`。进行中时可返回：

```json
{"task_id":"task-001","status":"running","progress":60}
```

完成后可返回：

```json
{"task_id":"task-001","status":"completed","output":"最终结果。"}
```

这些业务状态名、查询地址和查询间隔均须由接口约定；202 本身不会自动提供轮询能力。`Retry-After: 3` 在此示例中提示等待 3 秒再查询。

### 与回调、流式输出的区别

- **轮询**：客户端反复问“做好了吗？”。
- **Webhook**：服务端通过另一次请求通知“做好了”。
- **SSE / NDJSON**：通常通过已经打开的响应流持续传送消息。

适合报告生成、批量评测、长流程 Agent 任务。调用方应处理失败、取消、超时和结果过期，按建议间隔或退避策略查询，避免高频请求。设计参考 [Microsoft：异步请求响应模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply)。

长轮询是相关变体：一次查询先等待新结果或超时再返回，客户端随后再次查询；它仍是一系列 HTTP 请求，不等于 SSE。

## 9. 文件 / 下载流：返回文件内容或下载地址

### 9.1 直接返回文件内容

适合 PDF、Excel、图片、音频、压缩包等。返回 PDF 的响应头示例：

```http
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment; filename="report.pdf"
```

其后响应体是 PDF 的字节内容，不是描述文件的 JSON。

其他常见类型包括 `audio/mpeg`、`image/png`、`text/csv`、`application/zip`；`application/octet-stream` 表示通用二进制数据，并不是所有文件都应使用它。

`Content-Disposition: attachment` 提示按附件下载，并可提供文件名。参见 [MDN：Content-Disposition](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Disposition)。

### 9.2 先返回 JSON，再下载文件

```json
{
  "file_name": "report.pdf",
  "download_url": "https://files.example.com/reports/report.pdf",
  "expires_in": 3600
}
```

此时第一个接口返回的是 JSON 元数据，客户端需要再访问下载地址获取文件。示例中的 `expires_in` 表示链接有效期秒数，真实规则以接口约定为准。

### 接收和测试注意点

- 按字节保存文件，不要把二进制正文当成 JSON 或普通文本读取。
- 检查类型、文件名、文件是否可打开，以及接口提供的长度或校验信息。
- 文件下载可以分块进行，但不等于 SSE；字节逐步到达也不保证音视频能够立即播放，仍取决于媒体格式和客户端能力。
- 先检查状态码和 Content-Type，避免把错误 JSON 当成正常文件保存。

文件由后台生成时，可以组合“提交任务 → 轮询或回调 → 获取下载地址 → 下载”。

## 10. 其他需要认识的情况

- **分页 JSON**：每次返回一页完整数据，再通过页码或游标查询下一页；属于多次普通请求，不等于一条流。
- **multipart 响应**：一个响应体包含多个由 boundary 分隔的部分，每部分可有自己的类型。需要按分段格式解析，不等同于 NDJSON；也不要与上传请求中的 form-data 混淆。
- **消息队列 / 发布订阅**：服务把结果发送到队列或主题，消费者订阅接收。它是另一种异步系统集成方式，不一定属于 HTTP 接口响应。
- **GraphQL**：描述查询和执行模型，本身不能唯一决定输出方式；查询可返回普通 JSON，订阅等能力则依赖具体传输协议。

## 11. 面对一个未知接口，如何判断它怎么输出？

1. **先看接口协议**：HTTP、WebSocket 还是 gRPC。
2. **再看响应头**：`application/json`、`text/event-stream`、`application/x-ndjson`、文件类型等提供重要线索。
3. **检查实际内容**：完整 JSON、空行分隔的 SSE 事件、逐行 JSON，还是文件字节。响应头与正文必须一致，不能只凭其中一项断定。
4. **确认结果交付方式**：本次响应就是结果，还是只返回任务编号、轮询地址或下载地址？
5. **确认结束与错误规则**：正常完成由哪个事件、字段、状态或协议状态表示？中途失败怎么报告？

Apifox 在 HTTP 响应 Content-Type 包含 `text/event-stream` 时，会按 SSE 事件解析并支持时间线展示，见 [Apifox：SSE 调试](https://docs.apifox.com/sse)。

之前截图里的 `/agent/sse` 路径和 POST 方法提示它可能返回 SSE，但仅凭路径不能证实；应检查实际响应的 Content-Type 和事件结构。

## 12. 如何按需求选择，以及测试什么？

### 按需求选择

- 普通查询、短耗时任务：完整 JSON 响应通常最容易接入。
- 需要逐步展示文字或进度：SSE；若更适合逐行结构化记录，可采用 NDJSON。
- 需要持续双向发送、打断或实时语音：评估 WebSocket 或合适的流式 RPC。
- 内部服务间需要明确消息契约和流式调用：评估 gRPC。
- 任务时间长，调用方能接收通知：Webhook / 回调。
- 任务时间长，调用方不便开放接收地址：异步任务 + 轮询。
- 结果本质是文件：直接下载，或返回下载地址。

这些是基于交互需求的选择思路；调用已有接口时，应适配其现有协议。

### Agent / LLM 测试重点

- **完整性**：是否缺少片段、重复片段、乱码或记录解析错误？
- **拼接规则**：每次返回的是新增文本还是累计全文？累计全文不能直接反复追加。
- **完成判断**：HTTP 成功、任务完成和回答正确要分别判断。流已开始后，服务端可能无法再更换已发出的 HTTP 状态码，应按协议处理流内错误或异常断开。
- **时延**：区分请求开始、首个业务内容到达和最终完成；心跳或连接成功不算首段回答。
- **断连与重试**：是否丢消息、重复创建任务或重复处理回调？取消是否真正停止了任务？
- **内容质量**：最终回答是否准确、完整，是否符合预期业务规则？
