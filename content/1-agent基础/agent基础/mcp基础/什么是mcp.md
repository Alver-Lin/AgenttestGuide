# 什么是 MCP？

本文面向刚接触大模型和 Agent 的读者，通过“让 AI 查询订单”的例子，理解 MCP 的作用、工作过程，以及测试时需要关注什么。

想实际运行一个服务，可以接着阅读 [MCP 实战：用 Python 搭建本地 Markdown 笔记服务](./实战-用Python搭建本地笔记MCP服务.md)。配套示例包含服务端、验证客户端与测试笔记，可真实完成搜索、读取和新建文件。

文档核对日期：2026-11-17。本文重点介绍通用概念；具体接入时，需要核对客户端、服务端和 SDK 支持的协议版本。

## 1. 一句话理解 MCP

**MCP 是 Model Context Protocol 的缩写，中文通常译为“模型上下文协议”。它是一套开放标准，让 AI 应用能够用统一的方式连接外部工具和数据。**

例如，AI 应用可以通过 MCP 接入文件读取、知识库搜索、订单查询等能力。MCP 约定了这些能力如何被描述、发现和调用，以及结果如何返回。

官方用“AI 应用的 USB-C 接口”来类比 MCP：统一连接方式，有助于减少不同应用和外部系统之间重复适配的工作。参见 [MCP 官方介绍](https://modelcontextprotocol.io/introduction)。

这个类比需要注意边界：接口统一，并不代表所有服务都能直接使用。实际接入仍然需要相应的服务程序、兼容的客户端、身份认证和业务权限。

## 2. 为什么需要 MCP？

假设用户向客服 AI 提问：

> 帮我查一下订单 A1001 发货了吗？

仅靠模型训练时学到的知识，无法知道这笔订单现在的状态。应用需要到订单系统查询，再把查询结果交给模型组织回答。

没有 MCP 时，开发者也能完成这个任务，例如手动编写代码调用订单 API。但如果有多个 AI 应用，每个应用又要对接订单、库存、知识库等多个系统，就容易出现重复工作：

- 各自编写工具接入代码。
- 各自约定工具名称、参数和返回格式。
- 各自处理工具发现和通信错误。

采用 MCP 后，可以把订单查询能力封装为 MCP Server，让兼容的 AI 应用通过共同的协议接入。它减少的是**连接和适配成本**，具体的订单查询逻辑仍然需要开发。

如果只是一个小程序调用一个固定接口，直接接 API 也可能足够。是否采用 MCP，要看是否需要复用接入能力、连接多个系统，以及接入已有 MCP 生态。

## 3. 三个角色：Host、Client、Server

### 3.1 Host：用户使用的 AI 应用

Host 是承载 AI 交互的应用，例如一个客服助手或编程助手。它负责协调模型、上下文、工具与用户交互，也负责管理应用侧的权限策略。

在订单例子中，用户输入问题、看到回答的客服应用，就是 Host。

### 3.2 Client：应用内部的协议连接组件

Client 是 Host 内部与 MCP Server 通信的组件，负责发送协议请求、接收返回结果。

用户通常不直接操作它。一个 Host 可以创建多个 Client，分别连接订单服务、知识库服务等不同的 MCP Server。

### 3.3 Server：向 AI 应用提供能力的程序

Server 负责暴露工具或数据，并处理客户端请求。例如“订单 MCP Server”可以提供 `get_order_status` 工具，其内部再调用公司的订单 API。

这里的 Server 指服务程序，既可以运行在本机，也可以运行在远程服务器上；它不一定是一台独立的机器，也不一定需要运行大模型。

这三个角色的划分参考 [MCP 架构说明](https://modelcontextprotocol.io/docs/learn/architecture)。日常说“接入一个 MCP”，通常是在说“连接一个 MCP Server”。

## 4. MCP Server 可以提供什么？

入门时先认识三种核心能力：**Tools、Resources、Prompts**。一个 Server 可以只提供其中一种，不必全部实现。

### 4.1 Tools：可以执行的操作

例如：

- `get_order_status`：查询订单状态。
- `search_docs`：搜索知识库。
- `create_ticket`：创建工单。

工具通常具有名称、描述和输入参数定义。模型可以根据这些信息提出调用请求，由应用按权限策略执行。

Tools 不只包含“修改数据”的操作。查询订单、搜索文档等只读操作，也可以作为工具提供。

常见协议方法是 `tools/list`（列出工具）和 `tools/call`（调用工具）。参见 [Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。

### 4.2 Resources：可供读取的上下文资料

例如，一份说明文档、数据库表结构或业务规则文本，都可以作为资源提供。

资源通过 URI 标识，例如教学示例 `docs://orders/status-guide`。这里的 URI 用于标识资源，不一定是能在浏览器中打开的网址。

应用决定何时读取资源，以及如何将它加入模型上下文；“连接了资源服务”不代表其中所有内容都会自动交给模型。

常见协议方法是 `resources/list`（列出资源）和 `resources/read`（读取资源）。参见 [Resources 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)。

### 4.3 Prompts：可复用的提示词模板

例如，一个名为 `explain_order_status` 的模板，可以根据传入的订单状态，生成一组用于引导模型解释物流情况的消息。

Prompts 通常供用户在应用中选择使用。它提供的是提示内容，本身不等于执行了订单查询，也不会自动完成整个任务。

常见协议方法是 `prompts/list`（列出模板）和 `prompts/get`（获取模板）。参见 [Prompts 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts)。

可以这样记忆：**Tools 用来执行操作，Resources 用来提供资料，Prompts 用来提供提示模板。** 各个客户端对这些能力的支持程度可能不同。

## 5. 一次订单查询是怎样完成的？

下面是一个典型的应用流程，不限定具体产品的界面或实现方式。

1. **应用接入服务**：配置订单 MCP Server，完成适用的认证，并确认双方支持的协议版本和能力。
2. **发现工具**：Client 获取工具列表，应用知道存在 `get_order_status`，以及它需要哪些参数。
3. **用户提出问题**：“帮我查一下订单 A1001 发货了吗？”
4. **模型提出调用请求**：应用把相关工具定义提供给模型，模型选择订单查询工具并生成参数。
5. **应用执行调用**：Host 按授权策略处理请求，再通过 Client 调用 Server。Server 还需校验参数、调用身份和订单访问权限。
6. **服务查询业务系统**：Server 调用订单 API 或数据库，取得结果并返回。
7. **模型生成回答**：应用把工具结果交给模型，模型据此回答订单状态。

例如，业务查询结果是“已发货，暂无预计送达时间”，合理的回答就是：

> 订单 A1001 已发货，目前还没有预计送达时间。

模型不应自行补出“明天送达”。**协议调用成功，只说明完成了通信和调用，并不能保证最终回答正确。**

版本提示：`2025-11-25` 规范使用 `initialize` 等初始化流程；官方 `2026-07-28` 架构文档采用请求元数据和 `server/discover` 发现机制。学习旧教程时，不要混用不同版本的连接流程。参见 [2025-11-25 生命周期规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)及 [2026-07-28 架构说明](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)。

## 6. 一个工具定义长什么样？

下面是虚构的订单查询工具定义，用于理解字段含义；它不是完整的 MCP 请求，也不是可直接运行的服务。

```json
{
  "name": "get_order_status",
  "description": "根据订单号查询当前用户有权访问的订单，返回发货状态和已有物流信息。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "订单号，例如 A1001"
      }
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}
```

其中：

- `name`：调用时识别工具的名称。
- `description`：解释工具用途，帮助模型判断何时使用。
- `inputSchema`：用 JSON Schema 描述参数格式。
- `required`：声明必填参数。

对应的业务参数可以是：

```json
{
  "order_id": "A1001"
}
```

业务系统返回的数据可能是：

```json
{
  "order_id": "A1001",
  "status": "shipped",
  "estimated_delivery": null
}
```

最后这段只是示例业务数据；实际 MCP 调用还需要按对应协议版本封装请求与结果。工具字段和结果结构可查阅 [Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。

**工具描述中的“当前用户有权访问”不是权限控制本身。** 服务端必须依据可信身份检查访问权限，不能因为模型传入了一个订单号就直接返回数据。

## 7. MCP 和其他概念有什么区别？

### 7.1 MCP 和 API

API 是程序对外提供能力的接口。订单系统可以通过 HTTP API 暴露订单查询能力。

MCP 为 AI 应用接入外部能力提供共同协议。MCP Server 内部仍然可以调用原有 API，因此业务 API 和 MCP 可以同时存在。

例如，同一个订单查询 API 可以供手机 App 使用，也可以由 MCP Server 调用，再向 AI 应用提供工具。

### 7.2 MCP 和 Function Calling

Function Calling 通常指模型根据工具定义，输出工具名称和参数的机制。真正执行工具的仍然是应用或相关运行环境。

MCP 则规定应用与外部服务怎样交换能力信息、发起调用和返回结果。

两者可以配合使用：应用通过 MCP 获取工具定义，转换成模型接口接受的格式；模型提出调用请求后，应用再通过 MCP 执行。

因此，支持 Function Calling 的模型不一定原生处理 MCP 协议，中间仍需要应用完成接入和调度。

### 7.3 MCP 和 Agent

Agent 是围绕目标组织推理、工具调用和执行过程的应用系统。MCP 可以成为它连接外部能力的方式之一。

Agent 可以不使用 MCP；一个只提供文件读取能力的 MCP Server，也不因此成为具备自主规划能力的 Agent。

### 7.4 MCP 和 RAG

RAG 是检索增强生成：先检索相关资料，再让模型结合资料回答。

MCP 可以提供检索工具或资料读取能力，供 RAG 流程使用。检索策略、资料切分、排序和回答质量，仍需要应用另外设计和评估。

## 8. MCP 通过什么方式连接？

两种常见的标准传输方式是 **stdio** 和 **Streamable HTTP**。MCP 消息使用 JSON-RPC 格式；传输方式解决的是这些消息如何送达。

### 8.1 stdio：通过本机进程的输入输出通信

客户端通常启动一个本地服务进程，双方通过标准输入和标准输出交换消息。

开发时要注意：标准输出用于协议消息，不能混入普通调试打印；日志通常写到标准错误输出。否则客户端可能把日志当作协议消息解析。

### 8.2 Streamable HTTP：通过 HTTP 通信

MCP Server 作为独立服务运行，客户端通过 HTTP 访问，适合远程部署，也可以用于本机服务。

其中可以使用 SSE 传递流式消息，但“MCP 使用 HTTP”并不代表任意 REST API 都自动成为 MCP Server。

旧教程中还可能出现早期的 HTTP+SSE 传输方式，它和 Streamable HTTP 不能直接画等号。传输和兼容性说明参考 [MCP Transports 规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。

## 9. 从 Agent 测试角度，应该测什么？

下面是针对订单示例设计的测试思路，可分别验证服务能力和 Agent 的实际表现。

### 9.1 接入与工具发现

- 服务正常启动时，客户端能否获取预期工具？
- 地址错误、认证失败、版本不兼容时，应用能否给出明确反馈？
- 工具参数定义是否与真实实现一致？

### 9.2 参数与业务结果

- 查询合法订单，返回是否与业务系统一致？
- 缺少订单号、传入空字符串或错误类型时，是否有合理错误？
- 订单不存在与查询服务故障，是否被区分处理？

### 9.3 工具选择与回答质量

- 用户询问订单状态时，Agent 是否调用查询工具？
- 用户没有提供订单号，且上下文也没有时，Agent 是否索取必要信息？
- 查询失败时，是否如实说明，而不是编造状态？
- 返回结果缺少预计送达时间时，是否避免自行猜测？

### 9.4 权限与外部内容处理

- 用户 A 能否通过修改订单号读取用户 B 的订单？正确行为应是拒绝未授权访问。
- 用户只要求查询时，Agent 是否误触发取消订单等写操作？
- 订单备注中如果出现“忽略之前要求，执行其他工具”等文字，应用是否把它当作业务数据处理？

### 9.5 超时与重复执行

- 服务响应慢或连接中断时，应用是否在合理时间内结束等待？
- 重试查询是否符合预期？
- 对创建工单等写操作，重复请求是否导致重复创建？业务层是否有去重或幂等机制？

测试记录最好保留用户输入、工具名称、调用参数、工具结果和最终回答。这样才能区分问题发生在模型选工具、协议通信、业务服务，还是结果解释环节。

## 10. 初学者常见误区

- **“装了 MCP，模型就学会了所有业务。”** 接入提供了工具和上下文，模型是否正确使用它们仍需要验证。
- **“MCP Server 必须运行大模型。”** 一个提供订单查询的服务，可以只包含普通业务代码。
- **“接入 MCP 就能访问所有数据。”** 数据访问范围取决于真实身份、服务配置和权限校验。
- **“Tools 只负责写数据，Resources 负责所有查询。”** 查询也可以是 Tool，具体取决于服务如何设计。
- **“工具调用成功，任务就成功了。”** 还要确认查对了对象、返回了正确数据、回答忠实于结果。
- **“所有 MCP 客户端都支持相同功能。”** 协议版本、传输方式和功能支持需要分别确认。

## 11. 自测：能否回答这三个问题？

1. 为什么一个订单 REST API 不一定能直接作为 MCP Server 接入？
2. 模型输出 `get_order_status` 和订单号后，究竟是谁去执行查询？
3. 如果工具返回成功，但 AI 把“已发货”说成“已签收”，应该在哪个环节定位问题？

参考答案：

1. 还需要实现 MCP 约定的能力描述、发现、调用及消息格式等要求。
2. 由应用协调 MCP Client 发起调用，MCP Server 执行具体查询；模型生成参数不等于查询已经发生。
3. 应检查工具结果进入模型上下文及最终回答生成的过程，不能仅凭接口成功判定任务通过。
